# Operating federated Hara taps

A Hara **tap** is an independently operated pair of Git repositories:

- an identity repository with public authorization policy;
- a package registry with reviewed publication requests and release records.

The official Hara pair is only a default. A user can trust any other pair, and
the failure of one tap does not stop a project locked to another tap.

## Create a tap

Bring an Ed25519 root signing key from your own signer or key agent. Hara only
accepts its public key and sends canonical policy bytes to `HARA_SIGNER`.

```shell
export HARA_SIGNER=/opt/acme/bin/sign-identity-policy
hara package tap init acme \
  --registry ./acme-packages \
  --identity ./acme-identity \
  --identity-root-key 0123...abcd
```

The command creates these safe-to-commit files:

```text
acme-identity/
  identity.edn          signed public policy
  identity.edn.sig      detached root signature
  README.md
acme-packages/
  registry.edn          tap pairing and root fingerprint
  requests/.gitkeep
  .github/workflows/verify-request.yml
  README.md
```

It also adds the local pair to the creator's tap store and prints the root
fingerprint. Initialise Git repositories, push them to your chosen hosting,
then replace local paths with their canonical Git URLs when distributing the
tap descriptor.

## Let others trust it

Publish the fingerprint independently of the tap's own registry—for example,
through a domain you control, a signed release announcement, or direct
verification with the operator. A recipient then runs:

```shell
hara package tap add acme \
  --registry https://github.com/acme/hara-packages.git \
  --identity https://github.com/acme/hara-identity.git \
  --identity-key sha256:...
hara package tap verify acme
```

Verification clones the identity policy, hashes its declared root public key,
compares it with the locally pinned fingerprint, and verifies the detached
Ed25519 policy signature before reading publisher grants.

## Operate it safely

Protect both default branches. The identity repository should accept only
reviewed public-key grants and revocations. Registry pull-request CI must:

1. verify the exact signed identity policy;
2. verify publisher authorization and the immutable signed source tag;
3. reproduce the archive and compare its digest;
4. create the registry attestation in a protected job.

Never give untrusted build jobs a release-upload token or a signing key. The
workflow generated by `tap init` intentionally fails until it is wired to a
pinned registry verifier; this makes an incomplete deployment fail closed.

Projects must use tap-qualified dependencies such as `acme:team/widget`. The
lockfile records the tap and identity provenance, so a matching archive can
remain usable from cache while a remote registry is unavailable.
